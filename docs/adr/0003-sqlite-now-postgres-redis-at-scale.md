# 0003: Database/cache technology choice (carried over from Phase 2)

## Status

Accepted.

## Context

Phase 2's `services/fhir-api` chose Postgres (durable relational storage,
indexed search columns alongside a full JSON resource payload) plus
Redis (cache-aside reads, explicit invalidation on write/delete rather
than TTL-only) -- see that service's README for the original rationale.
Phase 4's `services/model-serving` has a different storage problem:
the *serving* app is stateless (it loads a bundled model artifact from
disk once at startup -- see `docs/adr/0001-*.md`'s consequences and the
service README), but `training/train.py`/`training/promote_model.py`
need a real MLflow tracking + Model Registry backend, and the Model
Registry specifically requires a SQLAlchemy-compatible database (a plain
file-based tracking store doesn't support registry operations).

## Decision

SQLite (`sqlite:///mlflow.db`) for MLflow's tracking/registry backend in
this project, not Postgres -- but for reasons that lead to the *same*
conclusion Phase 2 reached, applied to a different situation:

- **Phase 2's Postgres choice was driven by durability and concurrent
  multi-client access** (many API requests hitting the same database).
  `training/train.py` has neither property: it's a single process,
  run once per CI job or local retrain, with no concurrent writers.
  SQLite's single-writer model is a perfect match, not a limitation,
  for that access pattern.
- **Zero infrastructure for a mechanism that only needs to prove itself
  correct.** Standing up a Postgres container just to demonstrate that
  MLflow's registry (`set_registered_model_alias`, version lookup,
  `search_model_versions`) genuinely works would add a service with no
  corresponding benefit at this scale -- CI already verifies the full
  train -> register -> promote -> export pipeline runs correctly (see
  `.github/workflows/model-serving-ci.yml`) without one.
- **A real, shared, multi-user MLOps deployment would need exactly what
  Phase 2 chose, for the same reasons Phase 2 chose it.** If this
  project had multiple data scientists training concurrently against one
  long-lived tracking server (rather than each CI run getting its own
  throwaway `mlflow.db`), that's a durable-storage-under-concurrent-write
  problem -- Postgres, not SQLite. `infra/terraform/s3.tf`'s artifact
  bucket comment makes this explicit: it exists for "a real multi-user
  deployment," which the demo tier doesn't need yet.

Redis-style caching doesn't have a direct analog in `model-serving` as
built: there's no per-request computation worth memoizing (the loaded
model *is* the cache -- see ADR 0001's consequences on why inference
stays synchronous and in-process). It would become relevant only if a
future version added expensive per-request preprocessing worth
memoizing across requests.

## Consequences

- `mlflow.db` is not safe for concurrent multi-writer access and isn't
  horizontally scalable -- acceptable for one-process-at-a-time training
  runs, not for a shared production registry serving multiple
  simultaneous training jobs.
- `mlflow.db`/`mlruns/` are gitignored, regenerated by running
  `training/train.py` (see `services/model-serving/README.md`) --
  there's no persistent, shared registry state across environments,
  only what a given run (local or CI) produces for itself. Promoting a
  model to the deployed serving image happens by re-running the
  train/promote/export pipeline and rebuilding the image, not by
  pointing a shared server at a new alias.
